# راه‌اندازی اتصال به سامانه مودیان

> **وضعیت پیاده‌سازی:** این ماژول نسخه‌ی ۱ API سامانه (روش «شناسه یکتای حافظه مالیاتی + کلید خصوصی»، مسیر `self-tsp`) را پیاده می‌کند.
> ساختار بسته، امضا و رمزنگاری با سند فنی سازمان و کتابخانه‌ی مرجع `snapp-market-pro/moadian` هماهنگ شده و با بردارهای تست همان کتابخانه
> (شماره مالیاتی، رقم کنترل Verhoeff، نرمال‌سازی) و یک سازمان شبیه‌سازی‌شده آزموده شده است.
> **با سرور واقعی سازمان آزموده نشده است.** پیش از هر ارسال در محیط اصلی، حتماً در **محیط آزمایشی (sandbox)** سازمان فاکتورهای نمونه بفرستید و نتیجه را در کارپوشه مقایسه کنید.
> نسخه‌ی ۲ API (گواهی امضای الکترونیک با JWS/JWE) پیاده‌سازی نشده است.

## پیش‌نیازها
1. ثبت‌نام در سامانه مودیان و دریافت **شناسه یکتای حافظه مالیاتی** (۶ کاراکتر) و **شماره اقتصادی**.
2. ساخت جفت کلید RSA و ثبت کلید عمومی در کارپوشه‌ی سامانه (طبق راهنمای «ارتباط با سامانه» در پرتال مودیان). نمونه دستورها:
   ```bash
   openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem   # کلید خصوصی (PKCS#8) — محرمانه نگه دارید
   openssl rsa -in private.pem -pubout -out public.pem                            # کلید عمومی برای ثبت در سامانه
   ```
3. دریافت **شناسه ۱۳ رقمی کالا/خدمت** هر کالا از فهرست رسمی سازمان (در فرم کالا، فیلد «شناسه کالا/خدمت (مودیان)»).
4. در بکند `ENCRYPTION_KEY` را تنظیم کنید (`openssl rand -hex 32`). کلید خصوصی با این کلید رمز می‌شود و هرگز به مرورگر برنمی‌گردد.
   **این کلید را گم نکنید؛ بدون آن کلید خصوصی ذخیره‌شده قابل بازیابی نیست.**

## تنظیم (برنامه ← تنظیمات ← اتصال به سامانه مودیان)
1. محیط **آزمایشی** را انتخاب و شناسه حافظه، شماره اقتصادی و کلید خصوصی (PEM) را وارد و «ذخیره» کنید.
2. «دریافت کلید از سازمان» (کلید عمومی و شناسه‌ی آن از سرور گرفته می‌شود).
3. کد واحد اندازه‌گیری هر واحد را از فهرست سازمان وارد کنید («عدد» = `1627`).
4. «آزمون اتصال»؛ در صورت موفقیت «فعال‌سازی ارسال».

## ارسال
- در صفحه‌ی هر فاکتور فروش: «پیش‌نمایش بسته» (فهرست مشکلات + JSON با مبالغ ریالی) ← «ارسال به سامانه مودیان» ← پس از چند ثانیه «استعلام وضعیت».
- در فهرست فروش: «همگام‌سازی مودیان» همه‌ی در انتظارها را استعلام و فاکتورهای ارسال‌نشده را (به ترتیب تاریخ، حداکثر ۲۵ تا) ارسال می‌کند.
- فاکتور برگشت از فروش **با ارجاع به فاکتور اصلی** (`ins=4`) فقط پس از «ثبت‌شده» شدن فاکتور اصلی ارسال می‌شود. برگشتی مستقل از فاکتور (بدون ارجاع) قابل ارسال نیست.
- فاکتور ارسال‌شده قابل لغو نیست؛ برای اصلاح، فاکتور برگشتی صادر کنید.

## قواعد نگاشت (برای بررسی حسابدار)
| فیلد سامانه | منبع |
|---|---|
| `taxid` | ۶ کاراکتر شناسه حافظه + ۵ کاراکتر hex روز (از 1970) + ۱۰ کاراکتر hex سریال + رقم کنترل Verhoeff؛ هر تلاش جدید سریال تازه (شمارنده‌ی اتمی در جدول Integration) |
| `inno` | سریال داخلی به‌صورت hex ده‌رقمی |
| `inty` | ۱ اگر خریدار کد ملی ۱۰ رقمی یا شناسه ملی ۱۱ رقمی دارد؛ وگرنه ۲ |
| `inp` / `ins` | ۱ (الگوی فروش) / ۱ برای فروش، ۴ برای برگشت از فروش |
| `tob` / `bid` / `tinb` | ۱ حقیقی (۱۰ رقم) یا ۲ حقوقی (۱۱ رقم) / کد یا شناسه ملی خریدار / شماره اقتصادی خریدار |
| `prdis` / `dis` / `adis` | قیمت×تعداد / (قبل از تخفیف − بعد از تخفیف، شامل سهم تخفیف کل فاکتور) / مبلغ مشمول مالیات |
| `vra` / `vam` / `tsstam` | نرخ مالیات / مبلغ مالیات / مبلغ نهایی ردیف |
| `setm` / `cap` / `insp` | ۱ نقد، ۲ نسیه، ۳ نقد و نسیه / مبلغ نقدی / مبلغ نسیه |
| مبالغ | واحد پول پیش‌فرض **ریال** است (ضریب ۱)؛ فقط اگر `settings.currency = TOMAN` باشد با ضریب ۱۰ به ریال تبدیل می‌شود |

مواردی که پیش از ارسال بررسی و **مسدود** می‌شوند: نبود شناسه ۱۳ رقمی کالا، نبود کد واحد، شماره اقتصادی نامعتبر، ناهمخوانی جمع ردیف‌ها با جمع فاکتور، و برگشتی با فاکتور اصلی تأییدنشده.

## محدودیت‌ها و کارهای باقی‌مانده
- فاکتور اصلاحی (`ins=2`) و ابطالی (`ins=3`)، الگوهای غیر فروش (ارز، طلا، قبوض و …) و ارسال خودکار هنگام صدور فاکتور پیاده‌سازی نشده است.
- فیلدهای `tob` برای مصرف‌کننده‌ی نهایی و `pmt` در بخش پرداخت طبق نمونه‌ی مرجع مقداردهی شده‌اند؛ اگر سازمان رد کرد، متن خطا در صفحه‌ی فاکتور نمایش داده می‌شود.
- پاسخ استعلام به‌صورت دفاعی تفسیر می‌شود (`SUCCESS` / `FAILED` / در غیر این صورت «در انتظار»)؛ اگر قالب پاسخ سازمان فرق داشت، `MoodianService.inquire` را اصلاح کنید.
