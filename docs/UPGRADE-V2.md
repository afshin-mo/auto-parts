# ارتقا به نسخه ۲ — راهنمای اجرا

این نسخه ۱۲ قابلیت درخواستی را اضافه/تکمیل می‌کند. **این تغییرات روی سیستم شما اجرا و تست نشده‌اند** (محیط ساخت، دسترسی اینترنت/Postgres نداشت). قبل از استفاده‌ی واقعی مراحل زیر را به ترتیب انجام دهید.

## ۱) اجرا

```bash
cd backend
npm install
npx prisma generate
npx prisma migrate dev --name v2_branches_roles_codes     # مایگریشن جدید (اسکیما تغییر کرده)
psql "$DATABASE_URL" -f prisma/sql/001_search_indexes.sql  # ایندکس جستجوی شماره/نام (pg_trgm)
psql "$OWNER_DATABASE_URL" -v app_password='رمز-قوی' -f prisma/sql/002_rls.sql  # ایزوله‌سازی فروشگاه‌ها در دیتابیس (RLS)
npm run backfill:v2        # فقط اگر دیتابیس قدیمی دارید: شعبه‌ی مرکزی، شماره‌های جستجو، …
npm test                   # تست‌های جدید: permissions / branch / code-normalize
npm run start:dev

cd ../frontend && npm install && npm run dev
```

دیتابیس تازه: `npm run prisma:seed` (دو شعبه، فروشنده‌ی محدود به شعبه‌ی مرکزی، شماره‌های فنی).
اگر هنوز `backfill:v2` را اجرا نکرده باشید هم سیستم کار می‌کند: اولین درخواست هر فروشگاه، «شعبه مرکزی» را خودکار می‌سازد و انبارها را به آن وصل می‌کند؛ فاکتورهای قدیمیِ بدون شعبه فقط برای کاربران «همه‌ی شعبه‌ها» دیده می‌شوند.

## ۳) محدودیت‌ها و نکته‌های صادقانه

- **انتقال داده فقط از فایل اکسل/CSV** است، نه اتصال مستقیم به دیتابیس هلو/سپیدار/…؛ تطبیق ستون‌ها بر پایه‌ی عنوان‌های رایج فارسی است و روی خروجی واقعی هر نرم‌افزار آزمایش نشده؛ همیشه مرحله‌ی «تطبیق ستون‌ها» و «بررسی بدون ذخیره» را ببینید. فاکتورهای قدیمی منتقل نمی‌شوند، فقط مانده‌ی اول دوره‌ی حساب‌ها و موجودی.
- **سن بدهی تقریبی است** (مانده‌ی فعلی از جدیدترین فاکتورها پر می‌شود)، چون دریافت‌ها به فاکتور خاص تخصیص داده نمی‌شوند.
- **مانده‌ی طرف‌حساب سراسری است** (نه به‌تفکیک شعبه)؛ دریافت/پرداخت، فاکتور و چک به‌تفکیک شعبه ثبت و گزارش می‌شود.
- مانده‌ی اول دوره‌ی مشتری: مثبت = بدهکار به ما. تأمین‌کننده: مثبت = ما بدهکاریم. (در ویزارد با انتخاب «عدد مثبت یعنی …» خودکار تبدیل می‌شود و جمع بدهکار/بستانکار را قبل از ورود می‌بینید؛ با نرم‌افزار قبلی تطبیق دهید.)
- اسکن با دوربین به `BarcodeDetector` مرورگر و HTTPS نیاز دارد (کروم اندروید/سافاری جدید). بارکدخوان USB مثل صفحه‌کلید کار می‌کند.
- PWA فقط «نصب روی صفحه‌ی اصلی» است؛ **آفلاین کار نمی‌کند** (عمداً: داده‌ی انبار باید زنده باشد).
- `dev:mock` (پیش‌نمایش بدون بک‌اند) داده‌ی نمایشی ساده برای صفحات جدید دارد؛ رفتار واقعی را فقط با بک‌اند ببینید.
- نقش پایه‌ی کاربرِ دارای نقش دلخواه در دیتابیس `SALESMAN` ثبت می‌شود؛ دسترسی واقعی از نقش دلخواه می‌آید.

## ۴) تغییرات امنیتی مهم (بخوانید)

۱. **برند، دسته، واحد و خودروها قبلاً بین همه‌ی فروشگاه‌ها مشترک و قابل‌ویرایش بود**: مدیر یک فروشگاه می‌توانست برند را برای همه تغییر دهد و ورود گروهی هم برند/دسته‌ی «سراسری» می‌ساخت. اکنون `tenant_id` دارند (`null` = سیستمی، فقط SUPER_ADMIN)، و `backfill:v2` موارد ساخته‌شده توسط ورود گروهی را به فروشگاه صاحبشان نسبت می‌دهد.
۲. کنترل دسترسی از چند `@Roles` پراکنده به `@Perm('کلید')` منتقل شد (بیش از ۱۱۰ مسیر). تست `permissions.spec.ts` مطمئن می‌شود هر کلید استفاده‌شده در کاتالوگ هست. پیش‌فرض نقش‌های آماده از روی `@Roles` قبلی استخراج شده تا رفتار فعلی تغییر نکند؛ **تنها تفاوت:** مسیرهای خواندنیِ قبلاً بی‌قید (فهرست کالا، فروش، موجودی…) اکنون مجوز `*.view` می‌خواهند که همه‌ی نقش‌های آماده دارند.
۳. نقش دلخواه فقط مجوزی را می‌تواند بدهد که سازنده‌اش خودش دارد (جلوگیری از ارتقای دسترسی).

## ایزوله‌سازی فروشگاه‌ها در دیتابیس (RLS)

1. `prisma migrate` را با کاربر **مالک** اجرا کنید (روی دیتابیس دارای داده، ابتدا `prisma/sql/002_tenant_columns_existing_db.sql` را طبق توضیح بالای فایل در migration بگذارید).
2. `001_search_indexes.sql` و سپس `002_rls.sql` را با کاربر مالک اجرا کنید (ایدمپوتنت؛ بعد از هر migrate که جدول تازه می‌سازد دوباره اجرا کنید، وگرنه خطا می‌دهد).
3. `DATABASE_URL` **برنامه** را روی کاربر `auto_parts_app` بگذارید. migrate، seed و `backfill:v2` با کاربر مالک اجرا شوند (مالک از RLS معاف است).
4. تست: `E2E_DATABASE_URL=<کاربر برنامه> npm run test:e2e` (فروشگاه B هیچ‌چیز از A نمی‌بیند).

هر کد جدیدی که **پیش از شناخته‌شدن فروشگاه** به دیتابیس می‌رسد (مثل ورود) باید در `tenantContext.asSystem(...)` اجرا شود؛ در غیر این صورت چیزی نمی‌بیند. کار پس‌زمینه یا اسکریپت برای یک فروشگاه از `tenantContext.asTenant(id, ...)` استفاده کند. شکل آرایه‌ای `$transaction([...])` پشتیبانی نمی‌شود. بازگشت اضطراری: دستور آخر `002_rls.sql` (غیرفعال‌کردن RLS) و برگرداندن `DATABASE_URL` به کاربر مالک.

### نکته‌های نوشتن کد با RLS و تراکنش

- داخل callback یِ `$transaction(async (tx) => …)` هر کوئری Prisma را **await** کنید؛ کوئری تنبل اگر بیرون از callback اجرا شود، تراکنش بسته شده و خطای `P2028` می‌گیرید.
- برای چند کوئری پشت‌هم (لیست + شمارش، گزارش) از یک `$transaction` استفاده کنید، نه چند `Promise.all` جدا؛ هر کوئری تکی یک تراکنش مستقل است.
- کوئری خام با قطعه‌های `Prisma.sql` (مثل `branchSql`) را فقط روی `tx` اجرا کنید، نه روی `this.prisma.$queryRaw(...)` (قطعه‌ی تو در تو از افزونه‌ی کلاینت سالم رد نمی‌شود).
- اگر نقش یا وضعیت کاربر را در جایی تازه تغییر می‌دهید، `authUserCache.clear(userId)` را صدا بزنید.

## فروش سریع آفلاین (`/pos`)

- **بکند:** ستون تازه‌ی `invoices.client_request_id` (اختیاری، یکتا per-tenant). `prisma migrate` خودش می‌سازد؛ روی داده‌ی موجود مشکلی ندارد. `POST /sales` فیلدهای اختیاری `clientRequestId` (ارسال دوباره‌ی همان کلید = همان فاکتور) و `payInFull` (تسویه‌ی کامل با مبلغ محاسبه‌ی سرور) را می‌پذیرد.
- **سرور وب:** برنامه باید روی **HTTPS** باشد (service worker و `crypto.randomUUID` به آن نیاز دارند). فایل `/sw.js` را با `Cache-Control: no-cache` بدهید (نامش هش ندارد) و مسیرهای SPA را به `index.html` برگردانید. service worker فقط پوسته‌ی برنامه را کش می‌کند؛ پاسخ API هرگز کش نمی‌شود.
- **دامنه:** فقط فروش نقدی بدون مشتری. فهرست کالا (با موجودی شعبه‌ی فعال) هنگام باز کردن صفحه (اگر قدیمی‌تر از ۶ ساعت بود) روی دستگاه ذخیره می‌شود؛ پس هر روز یک بار باید صفحه با اینترنت باز شود. موجودی آفلاین تقریبی است؛ اگر سرور به‌خاطر کم‌موجودی فروشی را رد کند، در «صف ارسال» با علت می‌ماند و باید دستی تکلیفش روشن شود.
- **امنیت داده:** صف فروش و فهرست کالا در IndexedDB مرورگر می‌ماند و با خروج از حساب پاک نمی‌شود (تا فروش ارسال‌نشده گم نشود). فقط فروشگاهِ همان فروش اجازه‌ی ارسالش را دارد. روی دستگاه مشترک این را در نظر بگیرید.
- **بازنشانی رمز کاربر** (تنظیمات ← کاربران): نشست‌های فعلیِ آن کاربر تا انقضای توکن معتبر می‌مانند (توکن‌ها بی‌حالت‌اند). اگر حساب لو رفته، کاربر را همزمان غیرفعال کنید.

### عیب‌یابی RLS

- خطای `role "auto_parts_system" does not exist` (نسخه‌های قبلی این بسته): `002_rls.sql` روی دیتابیس اجرا نشده بود. حالا برنامه هنگام شروع وضعیت را تشخیص می‌دهد و بدون آن اسکریپت هم کار می‌کند (فقط با فیلترهای سطح برنامه) و در لاگ هشدار «RLS فعال نیست» می‌دهد.
- هشدار «کاربر دیتابیس … سوپریوزر یا مالک جدول‌هاست»: `002_rls.sql` اجرا شده ولی `DATABASE_URL` هنوز روی کاربر مالک/`postgres` است؛ Postgres برای چنین کاربری RLS را اعمال نمی‌کند. آدرس را روی `auto_parts_app` بگذارید.
- هیچ‌کدام از دو هشدار در لاگ نباشد یعنی ایزوله‌سازی دیتابیس واقعاً فعال است.

## ورود فاکتورهای خرید دریافتی، جستجو و قیمت فروش

- **ورود فایل:** «انتقال از نرم‌افزار قبلی» ← «فاکتور خرید دریافتی» ← فایل اکسل. ستون‌ها خودکار تطبیق می‌خورند (سریال، مارک، توضیحات، تعداد، قیمت کل، شماره فاکتور، تاریخ، شناسه کالا).
- **سریال و مارک کجا می‌روند؟** سریال ← «شماره قطعه سازنده» (`partNumber`)، مارک ← «برند» (`brand`)، و کد کالا (`sku`) = `سریال-مارک` (مثلاً `500655-PT6`)؛ چون یک سریال با مارک‌های مختلف، کالاهای جداست و کد کالا باید یکتا باشد. هر سه در جستجو پیدا می‌شوند (حتی با هم: `500655 PT6`).
- **قیمت:** مبالغ فایل به ریال و بدون تبدیل وارد می‌شود. قیمت خرید هر واحد = «قیمت کل» ÷ تعداد (تخفیف و مالیات داخل آن است). قیمت خرید کالا = بهای جدیدترین فاکتورِ آن کالا؛ هر ورود موجودی با بهای واحد خودش، و شماره‌ی فاکتور و تاریخ در توضیح حرکت انبار ثبت می‌شود. قیمت فروش ثبت نمی‌شود.
- **ورود دوباره‌ی همان فایل** موجودی را دو برابر نمی‌کند (ردیفی با همان کالا، انبار، شماره‌ی فاکتور و تعداد «بدون تغییر» حساب می‌شود).
- **سقف طرح:** اگر طرح فروشگاه سقف تعداد کالا دارد (طرح آزمایشی: ۱۰۰)، ورود بیش از آن با پیام «سقف تعداد کالاهای طرح پر شده است» رد می‌شود. سقف `max_products` را در جدول `tenants` بالا ببرید.
- **جستجو:** هر کلمه در نام، سریال، کد، بارکد یا مارک پیدا می‌شود؛ حروف عربی (ي ك) و فارسی (ی ک) و ارقام فارسی/لاتین یکی حساب می‌شوند. ورودی‌های جدید خودبه‌خود نرمال ذخیره می‌شوند؛ برای داده‌ی **قبلی** یک بار `psql -U postgres -d <db> -f prisma/sql/003_normalize_letters.sql` را اجرا کنید (ایدمپوتنت).
- **قیمت فروش** هنگام ساخت یا ورود کالا اختیاری است و هنگام فاکتور فروش نوشته می‌شود (کالای بدون قیمت در فاکتور فروش باید قیمت بگیرد). **مالیات بر ارزش افزوده** در فروش فوری و فاکتور فروش اختیاری است و درصدش را خودتان می‌نویسید؛ آخرین مقدار روی همان دستگاه یادآوری می‌شود.

### فایل فاکتور در دیالوگ «ورود از فایل» (صفحه‌ی کالاها)

- اگر فایل شبیه فاکتور خرید باشد (سریال + نام + تعداد و «قیمت کل» یا «شماره فاکتور»)، دیالوگ آن را تشخیص می‌دهد و با یک کلیک همان فایل را (بدون آپلود دوباره) به «فاکتور خرید دریافتی» می‌برد؛ در ویزارد هم اگر نوع «کالاها» انتخاب شده و فایل فاکتور باشد، همین پیشنهاد نمایش داده می‌شود.
- **قیمت خرید = قیمت کل ÷ تعداد** (و ریال ÷ ۱۰). اگر ستون «قیمت کل» نگاشت نشده و این گزینه روشن باشد، ورود متوقف می‌شود و بی‌صدا به «قیمت واحد» برنمی‌گردد.
- **یک کالا با چند قیمت** (خرید نقدی و اعتباری) خطا نیست. در ورود فاکتور هر ورود با قیمت خودش ثبت می‌شود و قیمت خرید کالا همان جدیدترین فاکتور (بر اساس تاریخ) است؛ در ورود کالا (دیالوگ و ویزارد) ردیف‌های هم‌کد در یک ردیف ادغام می‌شوند: تعداد جمع و قیمت از آخرین ردیف. تعداد ردیف‌های ادغام‌شده نمایش داده می‌شود.
- «ردشده» یعنی کالا از قبل در فروشگاه بوده، نه ردیف تکراری. ستون «قیمت فروش» دیگر ستون ضروری نیست.
